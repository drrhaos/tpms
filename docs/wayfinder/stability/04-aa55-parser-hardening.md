## Question

Какие проверки добавить в `Aa55SerialProtocol`, чтобы мусор не превращался в датчики и тревоги? Кандидаты: принимать только известные типы/длины кадров; белый список tireCode; ресинхронизация по одному байту при неверной контрольной сумме вместо удаления всего кадра; правдоподобие значений (скачок давления/температуры относительно прошлого кадра того же колеса); новый датчик принимается только после N согласованных кадров. Что из этого делать, с какими параметрами, и как это переносится на HID-протокол.

## Подсказки

- Из [Откуда фантомная запаска SP в v1.1.3](01-phantom-spare.md): кадр с неизвестным кодом шины (POS) должен отбрасываться, а не превращаться в `SENSOR_XX` (`Aa55SerialProtocol.kt:166`).
- Из [Что означают байты статуса и коды шин в протоколе 55AA](03-aa55-status-flags.md): бит «нет сигнала» — `0x20`; есть кадры других типов (`09`, `06 18`, `07 30`).

## Resolution

Решено с drhaos (2026-10-04), на основе [Сколько мусорных кадров пропускает парсер AA55](02-aa55-garbage-rate.md) и [Что означают байты статуса и коды шин в протоколе 55AA](03-aa55-status-flags.md):

1. **Парсер AA55:** побайтовый ресинк при неверной контрольной сумме (сдвиг на 1 байт вместо удаления всего `length`); кадр с неизвестным кодом шины (не `00/01/10/11/05`) отбрасывается, `SENSOR_XX` больше не создаётся. Белый список длин и проверка правдоподобия скачков — **не делаем** (по цифрам почти бесполезны / риск скрыть реальный прокол).
2. **Подтверждение значения — общий фильтр после любого парсера** (AA55 и HID, живёт в конвейере `DongleSession`): новое значение слота принимается, когда за 5 с пришло два **точно совпадающих** кадра (давление, температура, флаги). Ресивер AA55 повторяет кэш слота, так что задержка ≈ один цикл. Для HID проверить на устройстве, повторяет ли донгл значения; если нет — пересмотреть (допуск). Подтверждение **тревог** — отдельно, в [Нужно ли подтверждать тревогу перед показом](05-alert-confirmation.md).
3. **Статус и заряд:** «нет сигнала» = `0x20` (не `0x80`). Биты статуса становятся **флагами датчика** (`noSignal`, `leak`, `lowBattery`), а не напрямую `alertType`; какие тревоги из них следуют — решает тикет 05. Модель: `batteryPercent: Int?` (null — протокол не даёт процентов, как AA55) + `lowBattery: Boolean`; UI показывает процент для HID и только значок «низкий» для AA55.
4. **Другие кадры:** кадр `09` разбирается (ID датчика по слоту, признак «слот пуст» `55 AA 09 05 00 00 00 ..`); остальные известные типы (`06 18`, `07 30`, `06 00 88`, `06 B5`) распознаются и пишутся в диагностику. Запрос ID `0x07` шлётся при открытии и для AA55, и для Deelife; периодический запрос — в [Как определять потерю датчика, если ресивер повторяет последнее значение](10-sensor-loss-detection.md).
