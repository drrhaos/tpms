## Destination

Спецификация `docs/specs/stability.md` — приоритизированный список изменений, после которых TPMS Monitor стабильно работает на всех устройствах (эталон проверки — Teyes + CH340/AA55): надёжный реконнект донгла после сна/запуска машины, отсутствие ложных тревог и фантомной запаски SP, устранение USB-рисков (зависший `bulkTransfer`, параллельный опрос, `probe()` ворующий байты). Каждый пункт описан так, чтобы отдельная сессия могла его реализовать.

## Notes

- Домен: Android foreground-сервис, USB host, протокол AA55 (см. `AGENTS.md`, `data/usb/`).
- Режим: **планирование**. Тикеты принимают решения; код не правим, кроме тестов/скриптов, нужных для решения.
- Сырых логов с машины **не будет** — гипотезы проверяем по коду и на синтетических кадрах.
- Gradle/Android SDK в Linux-VM нет: синтетику гоняем на Python/Java-порте парсера; настоящие unit-тесты запускает человек на Windows.
- Охват: все устройства/протоколы; новые протоколы — вне.
- Скиллы для сессий: `grilling`; для решений о границах модулей — `codebase-design`.
- Когда тикетов не останется — собрать `docs/specs/stability.md` из Decisions so far.
- Спецификация собрана: [docs/specs/stability.md](../../specs/stability.md) (2026-10-26).

## Decisions so far

<!-- одна строка на закрытый тикет -->

- [Что означают байты статуса и коды шин в протоколе 55AA](03-aa55-status-flags.md): формат и масштабы в коде верны; бит «нет сигнала» — `0x20`, а не `0x80`; `0x08` кратковременный; ресивер вечно повторяет последнее значение слота, пустой слот SP шлёт фиктивное значение.
- [Как прервать зависший bulkTransfer на Android](07-bulk-transfer-unblock.md): `withTimeout` и `close()` зависание не прерывают, `releaseInterface()` прерывает; надёжнее reader-поток на `UsbRequest` + бесконечный `requestWait()` и пошаговое восстановление вплоть до перезапуска процесса.
- [Откуда фантомная запаска SP в v1.1.3](01-phantom-spare.md): пути для метки SP при выключенной запаске на HEAD нет; вероятный «фантом» — мусорный `SENSOR_XX` (неизвестный POS в AA55), который через fallback `elementAtOrNull` занимает пустой слот и затем даёт ложный SENSOR_LOST; запасная гипотеза — флаг запаски на деле включён (переключатель только в расширенном режиме / backup / импорт).
- [Хронология от пробуждения магнитолы до первого кадра](09-wake-timeline.md): реконнект медленный (debounce 5 с, поиск раз в 5 с, watchdog 15–20 с) и местами не восстанавливается; прямые баги без выбора — SCREEN_ON только в манифесте (wake-эскалация мертва), `CHECK_NOW`/`PROBE_USB` без `startForeground`, USB-разрешение с `FLAG_IMMUTABLE`, донгл узнаётся по VID:PID вместо `deviceName` — идут в спецификацию как есть.
- [Кто единственный владелец чтения USB](06-usb-read-ownership.md): `DongleSession` на каждое открытие (один reader-поток на `UsbRequest`, общий для serial и HID); `CHECK_NOW` только будит, `probe()` удаляется; смерть сессии — DETACHED/`deviceList`/ошибка/15 с тишины; донгл по `deviceName`; UI по изменению ≤1/с + таймер 30 с.
- [Сколько мусорных кадров пропускает парсер AA55](02-aa55-garbage-rate.md): мусор возникает только из повреждённого потока (сейчас — `probe()`/параллельные чтения), до ~2.5 ложных кадров в час, тревоги в основном через биты статуса; белый список почти бесполезен, побайтовый ресинк спасает целые кадры, подтверждение ×2/5 с убирает вред.
- [Какие сигналы шлют FYT/Teyes при включении зажигания](12-teyes-acc-broadcasts.md): FYT-интенты ACC в манифестный ресивер не приходят; `BOOT_COMPLETED` только при холодном старте; SCREEN_ON/OFF приходят при каждом сне, но лишь в runtime-ресивер; сток `com.syu.ms` часто убивает сторонние процессы во сне (`killAppWhenSleep`); `USB_DEVICE_ATTACHED` после сна может не прийти.
- [Как защитить парсер AA55 от мусорных кадров](04-aa55-parser-hardening.md): побайтовый ресинк + отброс неизвестных кодов шин; общий фильтр «два одинаковых кадра за 5 с» после любого парсера; «нет сигнала» = `0x20`, биты статуса → флаги датчика, `batteryPercent: Int?` + `lowBattery`; кадр `09` разбирается, `0x07` при открытии для AA55 и Deelife.
- [Нужно ли подтверждать тревогу перед показом](05-alert-confirmation.md): тревоги сразу после подтверждённого чтения, кроме `leak` (≥ 15 с); гистерезис при снятии (10 кПа / 3 °C), батарея залипает на 10 мин; таймаут по кадрам больше не SENSOR_LOST; память тревог в репозитории, `AlertEvaluator` чистый.
- [Как обрабатывать зависшее чтение USB](08-stuck-read-handling.md): механизм 06/07 остаётся; застрявший reader → переоткрыть, второй → рестарт процесса (kill + START_STICKY, ≤ 1 за 30 мин, иначе статус); 3 молчащих сессии → статус и пауза 30 с; у HID нет порога тишины, правило 90 с — только при идущих байтах; политика — чистый `SessionRecoveryPolicy`.
- [Чем будить сервис при пробуждении магнитолы](13-wake-trigger.md): любой runtime `SCREEN_ON` (все устройства) → сброс recovery, поиск с 1 с, детектор suspend (`elapsedRealtime − uptimeMillis`): был сон → переоткрыть любую сессию, иначе мягкий probe; `WakeEscalationScheduler` удаляется; ACC-интенты только в лог; решение в `SessionRecoveryPolicy.onWake`; автозапуск после сна — первый пункт шага Teyes в онбординге; диагностика «убит во сне».
- [Как определять потерю датчика, если ресивер повторяет последнее значение](10-sensor-loss-detection.md): AA55 — только бит `0x20` ресивера, своего критерия нет; HID — колесо «старое» после 15 мин без передачи (приглушено + «N мин», тревога важнее); общее «устарели» — по соединению, не по возрасту датчиков; `sensorTimeoutMs` удаляется; логика в чистом `SensorFreshness`.
- [Какие датчики допускать в слоты колёс](11-sensor-admission-policy.md): слот по умолчанию — метка AA55 или HID id 01–05 (без подстановки по порядку); пустой слот AA55 по кадру `09` не допускается; привязка послотовая; датчики вне слотов — только для привязки (без тревог, истории, снимка); пересчёт сразу при смене настроек; логика в чистом `WheelAssignment`.
- [Как получать и сохранять USB-разрешение](14-usb-permission-policy.md): сервис сам запрашивает разрешение раз на появление донгла + тихое постоянное уведомление и `UsbFault.NO_PERMISSION`; фильтр attach — на невидимую activity-трамплин (ассоциация «по умолчанию» без всплывания `MainActivity`); подсказка в онбординге; счётчик запросов в диагностике.
- [Нужны ли отдельные уведомления о тревогах](15-alert-notifications.md): да, только ALERT (давление, потеря датчика) — heads-up на колесо, звук при появлении/смене типа, снимается само; «Заглушить» реально глушит 30 мин; «Звук тревоги» → кнопка настроек канала; логика в чистой `AlertNotificationPolicy`.
