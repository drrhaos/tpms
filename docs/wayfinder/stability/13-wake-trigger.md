## Question

SCREEN_ON сейчас объявлен только в манифесте и не доставляется — wake-эскалация и `PROBE_USB` на пробуждение мертвы ([Хронология от пробуждения магнитолы до первого кадра](09-wake-timeline.md), B1). Какой триггер считать «пробуждением»: динамический SCREEN_ON в сервисе, OEM-сигнал ACC, `USB_DEVICE_ATTACHED`, их комбинация? Что делать по триггеру (сразу переоткрыть без debounce, поиск донгла с нарастающими паузами вместо фиксированных 5 с) и как это работает на не-Teyes устройствах.

## Подсказки

- Из [Какие сигналы шлют FYT/Teyes при включении зажигания](12-teyes-acc-broadcasts.md): надёжный сигнал только runtime SCREEN_ON/OFF (+ детектор сна по скачку wall-clock относительно uptime); процесс во сне часто убивается `killAppWhenSleep` — нужно решить, как пережить это (автозапуск FYT после сна, белый список, FrontApp, шаг онбординга), иначе ни один триггер не сработает.
- Из [Как обрабатывать зависшее чтение USB](08-stuck-read-handling.md): `SCREEN_ON` и `USB_DEVICE_ATTACHED` уже сбрасывают счётчик «молчащих сессий» и паузу 30 с; выбранный wake-триггер должен делать то же.

## Resolution

Grilling с drhaos, 2026-10-24. На момент решения рантайм-ресивер `SCREEN_ON/OFF` в сервисе уже был (тикет 06/08), debounce убран, поиск 1→5 с, донгл по `deviceName`. Решено:

**Триггер**
- Пробуждение = любой runtime `SCREEN_ON` в сервисе, без порога длительности сна, на всех устройствах (не только Teyes).
- FYT ACC-интенты (`com.fyt.boot.ACCON`, `com.glsx.boot.ACCON`, `android.intent.action.ACTION_MT_COMMAND_SLEEP_OUT`, `QUICKBOOT_POWERON`) — только логируем, в манифестном `BootReceiver` и в runtime-ресивере сервиса, для проверки на железе.

**Действие по триггеру** — одно, без повторов:
- сброс recovery (серия молчащих сессий, пауза 30 с, `DONGLE_SILENT`) — как в 08;
- пауза поиска возвращается к минимуму (1 с), поиск будится сразу;
- детектор suspend: на `SCREEN_OFF` запоминаем `elapsedRealtime − uptimeMillis`, на `SCREEN_ON` сравниваем; заметный рост (порядка секунд) = устройство реально спало → **любую** сессию (HID, AA55, Deelife) переоткрыть сразу; без suspend — мягкий probe (переоткрыть только потоковую сессию, молчащую > 5 с);
- `WakeEscalationScheduler` и `WakeEscalationReceiver` (5 будильников 5–120 с) удаляются; `PROBE_USB` с `force` остаётся для отладки/настроек.
- Решение — чистый `SessionRecoveryPolicy.onWake(recovery, suspended, состояние сессии)` → новое состояние + действие (переоткрыть / только разбудить поиск). Детектор suspend — маленький класс с инжектируемыми часами.

**Процесс убит во сне** (`killAppWhenSleep`):
- Онбординг Teyes, шаг 3: автозапуск после сна — первый пункт с пояснением («без этого мониторинг не переживёт сон») и кнопкой в настройки FYT; отметка ручная; шаг можно пропустить, пункт остаётся открытым в чеклисте настроек.
- Запуск из FrontApp / виджета / `MainActivity` → `start()` + разбудить поиск; recovery не сбрасывается (как ручная проверка в 08).
- Диагностика: время `SCREEN_OFF` в prefs; если новый процесс стартует, а предыдущий умер без `onDestroy`, не нашим рестартом (08), и последний heartbeat был после `SCREEN_OFF` → `serviceHealth` «убит во сне»; на Teyes подсвечиваем пункт автозапуска в чеклисте.

**Вне тикета:** нет USB-разрешения — тикет 14; «данные старые» — тикет 10.
