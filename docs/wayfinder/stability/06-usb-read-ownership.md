## Question

Сейчас `pollOnce()` может идти параллельно из цикла опроса, `ACTION_CHECK_NOW` и `ACTION_PROBE_USB`; `UsbConnection.probe()` читает из того же in-endpoint и выбрасывает байты; буфер AA55 и `lastSeen` не потокобезопасны. Какая модель владения: один reader-корутин/поток, которому остальные шлют сигналы (CHECK_NOW = «разбуди», PROBE = «переоткрой»); `Mutex` вокруг опроса; передача байтов из `probe()` в парсер. Как определять отключение донгла без чтения (USB_DEVICE_DETACHED, `deviceList`).

## Resolution

Решено с drhaos (2026-10-04):

- **Модель — один reader-поток на сессию.** Новый `DongleSession` создаётся на каждое открытие донгла и владеет соединением, reader-потоком (`UsbRequest.queue` + бесконечный `requestWait()`, см. [Как прервать зависший bulkTransfer на Android](07-bulk-transfer-unblock.md)), экземпляром парсера и записью (handshake/heartbeat). Наружу отдаёт Flow датчиков и событие «сессия умерла». Состояние парсера не переживает переоткрытие.
- **Один механизм для serial и HID** — `UsbRequest` работает и с interrupt-endpoint; отличается только парсер.
- **Сервис** создаёт и уничтожает сессию; **репозиторий** только принимает датчики из одного потребителя (запись через `_sensors.update {}`); цикл «опрос раз в 2 с» исчезает.
- **`CHECK_NOW`** не читает USB: только будит владельца (проверка наличия донгла/разрешения + обновление UI). `PROBE_USB` → «закрыть сессию и переоткрыть».
- **`probe()` удаляется.** Отключение/смерть = `USB_DEVICE_DETACHED`, исчезновение из `deviceList`, ошибка в reader-потоке или **15 с полной тишины** (настраиваемо; ресивер AA55 шлёт постоянно). Отдельный порог «байты идут, валидных кадров нет» остаётся (сейчас 90 с). Для HID порог тишины уточнить в [Как обрабатывать зависшее чтение USB](08-stuck-read-handling.md).
- **Донгл узнаётся по `deviceName`**, не по VID:PID (иначе после переэнумерации берётся мёртвое соединение).
- **UI / виджет / уведомление / оверлей** обновляются по изменению данных (не чаще 1/с) + таймер раз в 30 с для «возраста данных» и статусов.
