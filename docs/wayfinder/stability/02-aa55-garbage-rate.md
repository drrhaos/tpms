## Question

Порт `Aa55SerialProtocol.feed/extractFrame/parseFrame` на Python (или Java) и прогон синтетики: случайный шум; валидные кадры, порванные на куски произвольной длины; поток с выкушенными байтами (как от `probe()` / параллельного `read()`); смесь с шумом. AFK.

Измерить: долю ложно принятых кадров, их распределение по tireCode (особенно `0x05` → SP и неизвестные → `SENSOR_XX`), давлению/температуре (сколько из них пробивают пороги 150/350 кПа и 85 °C), потерю валидных кадров из-за удаления целого `length` при неверной контрольной сумме.

Результат: таблица цифр + скрипт как актив (ссылка из тикета).

## Resolution

Скрипт: [assets/aa55_fuzz.py](assets/aa55_fuzz.py) — побайтовый порт `Aa55SerialProtocol` + `SensorValidator` + `AlertEvaluator`, фиксированные seed'ы, самотест на векторах из исследования. Результаты: [assets/aa55_fuzz_results.txt](assets/aa55_fuzz_results.txt). Модель трафика: 1 кадр состояния / 0.5 с, 19200 бод. «Вредный» кадр = прошёл контрольную сумму, но значения не совпадают с исходным кадром.

| Сценарий | Вредных / час (сейчас) | С подтверждением ×2 / 5 с | Потеря целых кадров (сейчас → с побайтовым ресинком) |
|---|---|---|---|
| Чистый шум 10 МБ | 0 | 0 | — |
| Реальный поток (09/06/07, SP-заглушка, 0x20) без повреждений | 0 | 0 | 0 % |
| Потеря байтов 0.1 % + кража 1 % чтений | 0.2 | 0 | 0.68 % → 0.005 % |
| Потеря байтов 1 % + кража 5 % чтений | 2.1 | 0 | 5.7 % → 0.03 % |
| Реальный поток + повреждения | 2.5 | 0.04 | 5.4 % → 0.04 % |
| Шумовые всплески 5 % кадров | 0.8 | 0 | 0.15 % → 0 % |

Выводы:
- **Мусор рождается только из повреждённого потока** (потерянные/украденные байты), не из шума и не из реальных кадров других типов. Источник повреждений сейчас — `probe()` и параллельные чтения; решение [Кто единственный владелец чтения USB](06-usb-read-ownership.md) убирает его в корне.
- Вредные кадры почти всегда приходятся на **настоящие коды колёс** (FL/FR/RL/RR) и дают тревоги в основном через **биты статуса**: ложный SENSOR_LOST (бит `0x80`, который по исследованию неверен), LEAK→LOW_PRESSURE, BATTERY_LOW; пороги давления/температуры пробиваются редко.
- **Белый список длин и кодов (H1)** на повреждённом потоке почти не помогает (помогает только на искусственном шуме с заголовками).
- **Побайтовый ресинк (H2)** не снижает вред, но сокращает потерю целых кадров в ~100–200 раз.
- **Подтверждение двумя одинаковыми кадрами за 5 с (H3)** сводит вред к ~0 ценой задержки 5–15 % кадров на один цикл — естественно, раз ресивер постоянно повторяет значения.
- Фантомный SP из мусора — единичные случаи (2 на сценарий e'), `SENSOR_XX` — в основном на искусственном шуме.
