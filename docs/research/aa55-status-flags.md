# Протокол 55AA: байт статуса, коды шин, типы кадров

Исследование к тикету [03-aa55-status-flags](../wayfinder/stability/03-aa55-status-flags.md).
Сверяется с `app/src/main/java/com/tpms/app/data/usb/protocol/Aa55SerialProtocol.kt`, `DeelifeProtocol.kt`, `TpmsProtocolRouter.kt`.
Дата: 2026-10-02.

## TL;DR

- Формат кадра, XOR-чексумма, кодировка давления (×3.44 кПа) и температуры (−50 °C), коды шин `00/01/10/11/05` в кадре состояния: **код верен**, это подтверждают 6+ независимых источников (включая живые дампы и декомпиляцию APK).
- **Бит «нет сигнала» в коде неверен: `0x80` → должен быть `0x20`.** Значение `0x80` есть только в одном скрипте (cedricp, из него, по всей видимости, и взят код). Декомпилированный APK (`com.tpms`, `FrameDecode3`) и ещё два независимых проекта дают `0x20`.
- `0x08` = утечка (быстрая потеря давления) — подтверждено живыми наблюдениями. На практике флаг **кратковременный**: он появляется, когда датчик откручивают или накручивают, и потом сбрасывается.
- `0x10` = низкий заряд батареи — согласуются все источники, но вживую никто его не видел.
- Ресивер **бесконечно повторяет последнее закэшированное значение** каждого слота. Умерший датчик «замораживается» и не пропадает. Слот `05` (запаска) без датчика шлёт фиксированное фиктивное значение.

### 1.2 Кадр состояния шины (длина 8)

`55 AA 08 POS PRESS TEMP STATUS XOR`

| Поле | Значение | Источник | Уверенность |
|---|---|---|---|
| POS `00` | передняя левая | [TK], [HA] (проверено откручиванием), [ZU], [DL], [CED], [RM] | высокая |
| POS `01` | передняя правая | те же | высокая |
| POS `10` | задняя левая | те же | высокая |
| POS `11` | задняя правая | те же | высокая |
| POS `05` | слот запаски. **Без пятого датчика шлёт фиксированное фиктивное значение**: `46 46` (240.8 кПа / 20 °C) в [TK], 2.51 bar / 33 °C (`49 53`) в [HA], «internal reference, всегда включён» в [RM] | [TK], [HA], [RM] | высокая (что значение фиктивное), низкая (что сами байты постоянны у разных ресиверов) |
| Другие POS | не встречались ни в одном источнике (только 5 слотов) | — | средняя |
| PRESS | `raw × 3.44` кПа (≈ `raw × 0.5` psi; 0.5 psi = 3.447 кПа) | [TK] (проверено: `0x24` → 123.84 кПа = 1.23 bar совпало с манометром), [HA], [ZU], [DL] (`×0.5 psi`), [CED], [DOG] | высокая |
| PRESS (вариант) | «прямые PSI», raw = psi | только [RM], без сырых дампов. Скорее всего это ошибка автора: см. «Открытые вопросы» | низкая |
| TEMP | `raw − 50` °C | [TK] (проверено: `0x49` → 23 °C), [HA], [ZU], [DL], [CED], [DOG] | высокая |
| TEMP (вариант) | «прямые °F» | только [RM]. При ~22 °C значения `raw−50` °C и `raw` °F почти совпадают (73 → 23 °C = 73.4 °F), поэтому вероятна ложная интерпретация | низкая |

### 1.3 Байт STATUS (байт 6)

| Бит | Значение | Источник | Уверенность |
|---|---|---|---|
| `0x08` (бит 3) | **утечка / быстрая потеря давления** (hardware alarm) | [ZU] (APK), [TK] `decode.py`, [DOG], [CED], [DL]. Наблюдался вживую: [TK] (RL `24 → 0D → 0A → … → 00` со статусом `08`, затем `00`), [HA] («8 was seen on two wheels while air was escaping… then went back to 0»), [DL] («during a rapid pressure drop to 0.0 psi, the status immediately changes to 08») | высокая |
| `0x10` (бит 4) | **низкий заряд батареи датчика** (`low_power`) | [ZU] (APK), [TK] `decode.py`, [DOG], [CED]. Вживую не наблюдался | средняя–высокая |
| `0x20` (бит 5) | **нет сигнала от датчика** (`no_signal`) | [ZU] (APK, `status & 0x20`), [TK] `decode.py` (`0b00100000` = «Lost signal») и комментарий в README, [DOG] (`0b00100000`). Вживую не наблюдался | средняя–высокая |
| `0x80` (бит 7) | «нет сигнала» **только в [CED]** (`0b10000000`). Другие источники это не подтверждают | [CED] | низкая |
| `0x04` (бит 2) | «High temperature?» с вопросом | только [TK] `decode.py` | низкая |
| `0x02` (бит 1) | «High battery voltage??» с вопросом | только [TK] `decode.py` | низкая |
| `0x01` (бит 0) | «вероятно low battery» (догадка, не наблюдалось) | только [DL] | низкая |
| `0x00` | норма; при нормальной работе всегда 0 | [HA], [DL], все дампы [TK] | высокая |

Набор флагов `lowpower` / `leakage` / `nosignal` совпадает с полями broadcast в MTPMSU ([MT]) и с тремя флагами из APK ([ZU]). Значит, в оригинальном протоколе семантических флагов, скорее всего, ровно три.

Внутренние противоречия в [TK]. Комментарий в README: `0x20` = signal lost, `0x08` = low battery, `0x10` = leak. Псевдокод в README: `0x10` = signal lost **и** `0x10` = low battery (очевидная копипаста). Рабочий `decode.py`: `0x20` lost, `0x08` leak, `0x10` low battery. Верным считаем `decode.py`: он совпадает с APK [ZU] и с живыми наблюдениями `0x08` при спуске шины.

### 1.4 Другие кадры от ресивера

| Кадр | Значение | Источник | Уверенность |
|---|---|---|---|
| `55 AA 09 N ID0 ID1 ID2 ID3 XOR` | ответ на «query ID» (`0x07`): 4-байтный ID датчика. **Здесь N — порядковый номер `01`=FL, `02`=FR, `03`=RL, `04`=RR, `05`=SP, а не код `00/01/10/11`!** Пустой слот запаски: `55 AA 09 05 00 00 00 05 F6`, то есть ID ≈ 0 | [TK] (дамп + `decode.py`). [CED] и [DL] печатают N как есть | средняя–высокая |
| `55 AA 06 18 POS XOR` | подтверждение успешной привязки датчика (POS в кодировке `00/01/10/11/05`) | [TK] `decode.py` (`subcmd == 24`), [CED] (`array[3] == 0x18` → «Paired tire»); иначе «Pairing tire» | средняя |
| `55 AA 06 02 POS XOR` | «pairing success ACK» | только [DL], помечено как догадка | низкая |
| `55 AA 06 00 88 XOR` | запрос handshake/heartbeat от ресивера. В ответ [TK] шлёт heartbeat `0x19` (в Java-коде было `-120` = `0x88`) | [TK] `decode.py` | низкая |
| `55 AA 06 B5 xx XOR` | «ack with time?», xx меняется со временем (Java `-75` = `0xB5`) | [TK] `decode.py` | низкая |
| `55 AA 07 30 FROM TO XOR` | подтверждение перестановки колёс | [TK] `decode.py` (`subcmd == 48`), README | низкая–средняя |

### 1.5 Команды хоста → ресивер

Все команды — 6- или 7-байтные кадры с той же XOR-суммой (в [CED] она вычисляется явно через `calcCC`).

| Команда | Кадр (CRC пересчитан по XOR) | Назначение | Источник | Уверенность |
|---|---|---|---|---|
| `0x19` | `55 AA 06 19 00 E0` | heartbeat | [TK], [CED], [DOG] | высокая (байты), средняя (что он обязателен: [HA] вообще ничего не шлёт, и поток идёт) |
| `0x07` | `55 AA 06 07 00 FE` | запрос ID датчиков → пять кадров `09` | [TK], [CED], [DL] | высокая |
| `0x00` | `55 AA 06 00 00 F9` | eventACK / heartbeat-ack. [TK] шлёт его после **каждого** принятого кадра `08`/`09`/`06 18` | [TK], [CED], [DOG] | средняя (обязательность не доказана) |
| `0x01 POS` | `55 AA 06 01 POS CHK` | начать привязку датчика к позиции | [TK], [CED], [DOG], [DL] | высокая |
| `0x06` | `55 AA 06 06 00 FF`¹ | остановить привязку | [TK], [CED], [DL] | высокая |
| `0x58 0x55` | `55 AA 06 58 55 F4` | сброс ресивера | [TK], [CED], [DL] | средняя |
| `0x5B seed` | `55 AA 06 5B 20 82` | «encrypt»/seed: назначение неизвестно | [CED] (`encrypt_cmd`, seed `0x20`), [DOG] (`send_encryption(seed)`), [TK] («?? 55 AA 06 5B ?? E0») | низкая |
| `03 FROM TO` (len 7) | `55 AA 07 03 FROM TO CHK` | перестановка колёс между позициями | [TK], [CED], [DOG] | средняя |

¹ XOR(`55 AA 06 06 00`) = `FF`.

Аномалии контрольных сумм в источниках:
- [TK] и [DOG] шлют `querySensorID` как **7 байт** `55 AA 06 07 00 00 0C`, где `0C` — это **сумма** байтов, а не XOR. При длине `06` ресивер видит кадр `55 AA 06 07 00 00` с неверным CRC, и, судя по ответам в дампе, ему это не мешает. Значит, CRC входящих команд ресивер **возможно не проверяет**.
- `reset` в [TK] и [DOG] записан как `55 AA 06 58 55 E0`, хотя по XOR должно быть `F4`. `E0` похоже скопировано из heartbeat.
- [TK]: «calculated with XOR», но в одном месте написано «0x0C = 0x55+0xAA+…». Это единственное упоминание суммы, и дампы ему противоречат.

## 2. Расхождения с текущим кодом

| # | Где | Сейчас в коде | Что говорят источники | Уверенность | Рекомендация |
|---|---|---|---|---|---|
| 1 | `STATUS_NO_SIGNAL = 0x80` | «нет сигнала» = бит 7 | `0x20` (APK [ZU], [TK] `decode.py`, [DOG]). `0x80` есть только в [CED], откуда код, видимо, и перенесён (совпадают и `calcCC`, и имена `nosignal/leakage/lowbattery`) | средняя–высокая | Перейти на `0x20`. Как переходную меру можно считать «нет сигнала» = `0x20 or 0x80`. Логировать любые ненулевые статусы с сырыми байтами |
| 2 | `STATUS_LEAKAGE = 0x08` → `LOW_PRESSURE` без учёта давления | — | Бит верный. Но вживую он **кратковременный** и выставляется при откручивании или накручивании датчика ([HA], [TK], [DL]; [DL] даже использует его как этап привязки). Ложные тревоги при обслуживании колёс вполне возможны | высокая (смысл), средняя (риск ложных) | Оставить, но прогонять через подтверждение тревоги (тикет 05). Возможно, лучше отдельный `AlertType` вроде «быстрая утечка» |
| 3 | `STATUS_LOW_BATTERY = 0x10`, `batteryPercent = 5 / 50` | процент заряда | Бит верный. **Уровня заряда в протоколе нет**, есть только булев флаг. 50 % — выдуманное значение | высокая | В UI показывать «батарея OK / низкий заряд», а не проценты |
| 4 | Неизвестные биты (`0x01`, `0x02`, `0x04`, `0x40`) | игнорируются молча | Значения не подтверждены (догадки: `0x04` перегрев, `0x02` высокое напряжение, `0x01` батарея) | низкая | Не трактовать, но логировать (`TPMS_RAW`), чтобы собрать данные с реальных донглов |
| 5 | Слот `05` (SP) | парсится как обычный датчик | Без пятого датчика ресивер шлёт фиксированное фиктивное значение (`46 46`, `49 53`…) | высокая | Связано с тикетом 01 (phantom spare). Надёжный признак: ответ на `0x07` для слота 5 с ID `00 00 00 xx`. Альтернатива — «значение не меняется ни разу за N минут» |
| 6 | Детекция потери датчика | `SENSOR_LOST` только по биту и, видимо, по таймауту по `timestamp` | Ресивер **повторяет кэш вечно**, поэтому `timestamp` обновляется каждые ~2 с даже у мёртвого датчика. Таймаут по времени прихода кадров потерю датчика не обнаружит | средняя–высокая | Признак «давно не менялось» считать по изменению значений (pressure/temp), а не по приходу кадра. Опираться на бит `0x20` |
| 7 | Кадры длиной ≠ 8 | отбрасываются (`parseFrame` → null) | Существуют `09` (ID), `06 18` (pairing ok), `06 00 88`, `06 B5`, `07 30` | высокая | Пока отбрасывать нормально. Если понадобится ID: **у `09` своя нумерация позиций 1..5**, а не `00/01/10/11/05` |
| 8 | Хендшейк `0x19`, `0x07` (6 байт, payload `00`) | `55 AA 06 19 00 E0`, `55 AA 06 07 00 FE` | Байты совпадают с [TK] и [CED] | высокая | ОК. Ответ на `0x07` (кадры `09`) сейчас игнорируется |

## 3. Открытые вопросы

1. **Реальный бит «нет сигнала»** (`0x20` или `0x80`): ни в одном публичном дампе он не выставлен. Нужен эксперимент: снять датчик или вынуть батарейку и подождать (по аналогии с [HA] — до десятков минут), затем снять `logcat -s TPMS_RAW`. Заодно проверить, начнёт ли ресивер вообще ставить флаг или будет вечно повторять кэш.
2. **Флаг низкого заряда** (`0x10`) тоже вживую не наблюдался. Нужен датчик со слабой батареей или лабораторный БП.
3. **Донглы Teyes и «TPMS 100-A1»**: публичного реверса именно для них не нашлось. MTPMSU ([MT]) поддерживает «Deelife и Teyes» с теми же тремя флагами, но версия 2.4.6 «исправила совместимость с Teyes». Значит, у Teyes есть отличия, но какие — неизвестно (VID:PID? другой формат кадра? HID вместо CH340?). Нужен сырой дамп с реального донгла Teyes.
4. **TY05 / TY06 / «FrameDecode3»**: [DOG] различает аппаратные версии TY05 и TY06, но в коде их не разделяет. В APK есть `FrameDecode3`, значит, вероятно, существуют `FrameDecode1/2`, то есть другие версии протокола. Их форматы не найдены. Следующий шаг — декомпилировать оригинальное приложение `com.tpms` (TPMS для FYT/Teyes) и посмотреть `FrameDecode*`.
5. **Вариант [RM]** (давление в PSI, температура в °F напрямую). Сырых байтов в репозитории нет. Пересчёт показывает, что для температуры это, скорее всего, совпадение. Для давления разница двукратная (21 vs 10.5 psi), и это нельзя проверить без дампа. Пока считаем ошибкой интерпретации.
6. **Команда `0x5B` (encrypt/seed)**: назначение неизвестно. Возможно, у части донглов поток данных включается только после неё (привязка к «своей» магнитоле). Если какой-то донгл молчит после `0x19`, стоит попробовать `55 AA 06 5B 20 CHK`.
7. **Проверяет ли ресивер CRC входящих команд**: [TK] шлёт `query ID` с неверным CRC и получает ответ. Это не критично, потому что мы шлём корректный XOR.
8. **Фиктивные значения слота `05`**: зависят от прошивки или ресивера (`46 46` vs `49 53`). Нужно собрать с наших донглов и, возможно, сделать «отпечаток» по ответу `09 05 00 00 00 ..`.
